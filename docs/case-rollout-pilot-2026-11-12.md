# การทดลองนำร่อง: คำสั่งเดียวกันตั้งแต่เริ่มจนจบคดี

## คำถามวิจัย

เมื่อรับคำสั่งที่ตีความแล้วชุดเดียวกันตามลำดับ ตัวตัดสินแบบ Neural-only และส่วนตัดสิน Symbolic ของระบบ Neuro-symbolic จะรักษาสถานะและให้ผลจบคดีสอดคล้องกันหรือไม่?

รอบนี้แยกการตีความภาษาออกเพื่อศึกษาส่วนตัดสินโดยตรง จึงไม่เรียกว่า benchmark ของเกมครบระบบ ไม่วัด Neural parser, fast path, repair, reflexion, UI หรือความเข้าใจผู้เล่น และไม่นำเวลา Symbolic ไปอ้างว่าเป็นเวลา NeSy ตั้งแต่รับข้อความจนตอบผู้เล่น

## เงื่อนไขทดลอง

| รายการ | กำหนดไว้ก่อนเรียกโมเดล |
|---|---|
| เส้นทาง | walkthrough ที่มีอยู่ในโครงการ A 28 ตา, B 39 ตา, C 42 ตา |
| รอบเรียก API นำร่อง | A หนึ่งรอบ ไม่เกิน 28 ครั้ง; B/C ตรวจเส้นทางออฟไลน์เท่านั้น |
| ข้อมูลเข้าร่วมกัน | คดี กฎ กลไก สถานะเริ่มต้น และ ParsedCommand ทุกตา |
| Neural-only | GeminiGameProvider + NeuralGameMaster ได้ข้อมูลคดีทั้งหมดและต้องคืนสถานะใหม่เอง |
| NeSy ส่วนตัดสิน | SymbolicEngine ของคดีนั้น รับ ParsedCommand ชุดเดียวกัน |
| โมเดล | ใช้รุ่นจากการตั้งค่าโครงการ บันทึกชื่อที่ร้องขอใน manifest และรุ่นที่ตอบจริงใน metadata |
| อุณหภูมิ | 0 |
| สถานะระหว่างตา | ใช้ผลของตัวเอง ไม่คืนเป็นสถานะอ้างอิงและไม่แก้ความผิดให้ Neural |
| เวลาในเกม | elapsed_seconds = 0, started_at = null; เวลา API บันทึกแยก |
| จุดหยุด | คำสั่งหมด, ระบบคืนฉากจบ, หรือ provider/schema error |
| รูปแบบผิด | หยุดรอบ เก็บคำตอบดิบ/ชนิด error และจำนวนตาที่ยังไม่รัน ไม่มี fallback หรือ retry |
| การบันทึก | flush turns.jsonl ทุกตา เก็บ inputs, reference, prompt, hash, usage และ summary |

ทั้งสองฝั่งได้รับคำสั่งเหมือนกันตามตาที่ตรงกัน หากฝั่งหนึ่งจบก่อนหรือบริการขัดข้องจะไม่บังคับให้เล่นต่อ แต่บันทึกจำนวนตาที่ไม่ได้รัน ดังนั้นจำนวนคำตอบอาจไม่เท่ากัน

Neural ได้ข้อมูลกติกาและเนื้อเรื่องทั้งหมดเพื่อไม่ให้เสียเปรียบด้านแหล่งข้อมูล แต่ไม่ได้รับ reference trajectory หรือผลการตรวจของ Symbolic ใน prompt ข้อมูลอ้างอิงใช้วิเคราะห์ภายหลังเท่านั้น ไม่มีการเรียก Symbolic เพื่อซ่อมผลของ Neural

## ตัวชี้วัด

1. **ฉากจบที่ระบบรายงาน**: บันทึก ending_id ตามจริง ไม่ถือว่า true_ending อย่างเดียวพิสูจน์ว่าเล่นถูก
2. **จบตรงเส้นทางอ้างอิง**: ต้องได้คำตอบใช้ได้ครบทุกตาและสถานะสุดท้ายทุกฟิลด์ตรงเส้นทางอ้างอิง
3. **ตาแรกที่สถานะต่าง**: ช่วยชี้จุดเริ่มต้นของความผิดสะสม
4. **ความสอดคล้องกับเส้นทางอ้างอิง**: เทียบ allowed, state, visible_objects, visible_people, deductions, pillar_status รายตา
5. **ความสอดคล้องกับกฎบนสถานะของตัวเอง**: ใช้ Symbolic ประเมินคำสั่งบน state_before ที่ Neural สร้างจริง ตรวจหลังคำตอบโดยไม่ส่งผลกลับให้ Neural เพื่อแยกความต่างที่สะสมจากตาก่อนกับความต่างในการเปลี่ยนสถานะตานี้
6. **บริการและทรัพยากร**: จำนวนคำขอจริงในระดับ adapter, provider/schema error, latency และ usage ที่ provider ส่งมา ไม่ประเมินราคาเมื่อไม่มีราคาที่ตรวจสอบแล้ว

รายการในสถานะเปรียบเทียบโดยไม่สนลำดับแต่ยังตรวจสมาชิกซ้ำ ทุกฟิลด์ของ GameState ต้องปรากฏในคำตอบดิบ ตัว wrapper ของการทดลองปฏิเสธคำตอบที่ขาดฟิลด์ แม้ adapter รุ่นเดิมจะเติมค่าจากสถานะก่อนหน้าให้ก็ตาม

ตัวนับ attempts หมายถึงการลองเรียก provider จาก adapter ไม่ยืนยันว่าคำขอไปถึง Google ถ้าเกิด ConnectError หรือไม่มี usage

## บันทึกตรวจเครื่องมือก่อนรอบหลักของ pilot

- `results/case-rollout/2026-11-12-offline-abc`: ตรวจเส้นทาง Symbolic ครบ A 25, B 39, C 42 ตา ทุกคดีได้ true_ending
- `results/case-rollout/2026-11-12-live-a`: การเชื่อมต่อครั้งแรกใน sandbox เกิด ConnectError ไม่มีคำตอบโมเดล ไม่นับเป็นผลความสามารถ
- `results/case-rollout/2026-11-12-live-a-network`: เรียก Gemini จริง 3 ครั้ง ได้คำตอบใช้ได้ 2 ครั้ง สถานะสองตาแรกตรงอ้างอิง ตาที่ 3 ขาดหลายช่องของ new_state จึงหยุดตาม protocol เหลือ 22 ตาที่ยังไม่รัน
- พบว่า schema ที่ provider ได้รับใช้ GameState ซึ่งมี default ทำให้ฟิลด์สถานะไม่ใช่ required ทั้งหมด แม้ prompt และตัวตรวจจะกำหนดให้ส่งครบ จึงแก้เครื่องมือเป็น `case-rollout-1.1-required-state-schema` ให้ schema กับตัวตรวจตรงกัน
- เพิ่มการทดสอบตรวจ schema ที่คลี่และส่งให้ Gemini จริงว่าทุกช่องของ GameState อยู่ใน required รวมช่องที่อนุญาต null โดยไม่เติมค่าหรือแก้ความหมายของคำตอบ
- เก็บโค้ดรอบเดิมไว้ใน `code-snapshot` และเก็บผลเดิม ไม่รวมผล 3 ครั้งนั้นกับรอบใหม่ เริ่มคดีใหม่จากสถานะเริ่มต้น การเปลี่ยน schema เป็นการแก้เครื่องมือหลังรอบตรวจ ไม่ใช่หลักฐานว่าโมเดลรุ่นเดิมมีประสิทธิภาพเปลี่ยนไป
- ผู้ใช้อนุญาตรอบใหม่เพิ่มอีกไม่เกิน 25 ครั้ง เก็บแยกที่ `results/case-rollout/2026-11-12-live-a-required-schema` อ่านผลสำเร็จจริงจาก summary.json และ report.md ในโฟลเดอร์นั้น

## ผลรอบ schema ที่แก้แล้ว

Neural ได้คำตอบใช้ได้ 18 ตา สถานะตรงเส้นทางอ้างอิง 14/18 ตา เริ่มต่างที่ตา 7 และมีการเปลี่ยนสถานะต่างจากกฎบนสถานะของตัวเอง 2 ตา คือ 7 และ 18 การอนุญาต/ปฏิเสธตรงอ้างอิงครบ 18/18 ตา คำขอที่ 19 เกิด provider ClientError จึงหยุดตามแผน อีก 6 ตายังไม่ได้รัน ไม่มีการลองใหม่ใน episode นี้

Symbolic จบคดี A ครบ 25 ตา แต่ยังเปรียบเทียบการจบครบทั้งสองฝั่งไม่ได้ และห้ามนำ service failure ไปสรุปว่า Neural ให้เหตุผลแพ้ ดูตัวอย่างและตารางเฉพาะ 18 ตาที่มีผลคู่กันใน `results/case-rollout/2026-11-12-live-a-required-schema/findings.md`

## ที่มาของคำตอบอ้างอิงและข้อจำกัด

- ใช้ Symbolic engine replay walkthrough เพื่อสร้าง reference เป็น **software oracle จาก implementation เดียวกับฝั่งเปรียบเทียบ** ไม่ใช่คำตอบที่ผู้ตรวจอิสระเขียนไว้ การผ่าน 100% ของ Symbolic จึงเป็น self-consistency check ไม่ใช่หลักฐานอิสระว่า NeSy เหนือกว่า
- การตรวจออฟไลน์ยืนยันว่า A/B/C มีเส้นทางไป true_ending และทุกคำสั่งบนเส้นทางได้รับอนุญาตกับโค้ดปัจจุบัน
- ชุดนี้เป็น development walkthrough ที่มีแต่เส้นทางถูกต้อง จึงยังไม่วัดความทนทานต่อคำสั่งลวงหรือคำสั่งผิดเงื่อนไขอย่างครอบคลุม
- การทดลองหนึ่งรอบคดี A เป็นเพียง pilot ไม่มีการทดสอบนัยสำคัญทางสถิติ ห้ามนับ 25 ตาที่ต่อเนื่องกันเป็นตัวอย่างอิสระ 25 เกม
- การไม่พบความต่างหมายถึงไม่พบในเส้นทางและรอบนี้ ไม่ได้พิสูจน์ว่าสองระบบเท่าเทียมกันทั่วไป
- ความต่างของ state กับ reference ทุกตาหลังจุดแรกอาจเป็นผลสะสม ต้องอ่านคู่กับ own_state_rule_audit ไม่เรียกทั้งหมดว่าเหตุผิดกฎใหม่
- ไม่ตรวจความหมายของข้อความบรรยายอัตโนมัติ และไม่เรียกอัตราสถานะต่างว่าอัตรา hallucination ทั้งระบบ
- เอกสาร mechanics v1 ยังอธิบายการส่งหลักฐานกล่าวหาแบบเก่า จึงสร้าง v2 ให้ตรงกับการใช้หลักฐานทั้งหมดและการอนุญาตละ instrument เมื่อมีกุญแจแล้ว โดยเก็บ v1 ไว้สำหรับรอบประวัติศาสตร์

## วิธีรันซ้ำ

รันจากโฟลเดอร์โครงการ ใช้ชื่อโฟลเดอร์ผลลัพธ์ใหม่ทุกครั้ง สคริปต์ปฏิเสธการเขียนทับผลเดิม

```powershell
# ตรวจเส้นทาง A/B/C ออฟไลน์ ไม่เรียก API
.venv\Scripts\python.exe scripts\run_case_rollout_benchmark.py --cases A B C --output results\case-rollout\offline-new

# รัน Neural จริงคดี A สูงสุด 25 ครั้ง ใช้โควตาและส่งข้อมูลเกมไป Google Gemini
.venv\Scripts\python.exe scripts\run_case_rollout_benchmark.py --cases A --live --max-provider-calls 25 --output results\case-rollout\live-a-new

# ตรวจกลไกบันทึกผลและการส่งต่อความผิด ไม่เรียกโมเดล
.venv\Scripts\python.exe -m pytest tests\test_case_rollout_benchmark.py -q
```

การขยายไป A/B/C ครบทั้งสามต้องใช้สูงสุด 106 คำขอต่อรอบ ส่วนการทำซ้ำคดี A 3 รอบใช้สูงสุด 75 คำขอ ต้องกำหนดขอบเขตการรันก่อนและแยกจาก pilot นี้ ไม่รวมผลการปรับ prompt กลางทางเป็นรอบที่ตั้งค่าคงที่

## ข้อความสำหรับอธิบายอาจารย์

> เราใช้การทดลองแบบเล่นคำสั่งชุดเดียวกันต่อเนื่องตั้งแต่ต้นจนจบคดีครับ โดยควบคุมคดี กฎ สถานะเริ่มต้น และคำสั่งให้เหมือนกัน แต่ปล่อยให้แต่ละระบบใช้สถานะที่ตัวเองสร้างต่อไป เพื่อดูผลของความผิดพลาดสะสม รอบนำร่องนี้แยกการตีความภาษาออกและวัดเฉพาะส่วนตัดสิน ตรวจทั้งฉากจบ ตาแรกที่สถานะเริ่มต่าง และความสอดคล้องกับกฎครับ ชุดอ้างอิงตอนนี้สร้างจาก engine ของเรา จึงเป็นผลนำร่องสำหรับตรวจวิธีทดลอง ขั้นต่อไปต้องมีผู้ตรวจอิสระและชุดทดสอบใหม่ก่อนสรุปประสิทธิภาพทั่วไป

## ขั้นถัดไปของผลวิจัยหลัก

ให้ผู้ตรวจอิสระทบทวนหรือเขียน reference แยกจาก engine เพิ่มเส้นทางและคำสั่งผิดเงื่อนไขที่ไม่ใช้ปรับระบบ ทดลองซ้ำแบบจับคู่โดยตรึงโมเดลและการตั้งค่า แล้วแยกการทดลองรับข้อความภาษาธรรมชาติตั้งแต่ต้นเป็นอีกชุดหนึ่ง เพื่อแยกผลจากการเข้าใจภาษาออกจากผลของการตัดสินตามกฎ
