การทดลองที่สอง รอบแรก (ยังไม่ครบ)
==================================

โมเดล      gemini-3.5-flash-lite
รันได้     EP1 เท่านั้น (31 ตา) ส่วน EP2 EP3 ชนโควตารายวัน 500 calls
สถานะ      ⚠️ n=1 บท ยังน้อยเกินกว่าจะสรุป ต้องรัน EP2 EP3 ให้ครบก่อนรายงาน

ผล EP1 — บทที่ทุกคำสั่งถูกกฎหมด ผู้เล่นไม่ได้ทำอะไรผิดเลย
    โหมด A พาไปสู่สถานะที่เป็นไปไม่ได้ตั้งแต่ตาที่ 7
    โหมด A อยู่ในสถานะที่เป็นไปไม่ได้ 25 จาก 31 ตา (81%)
    โหมด B เป็นศูนย์
    สถานะสองโหมดเริ่มแตกที่ตาที่ 3

กลไกที่ทำให้พัง (ยืนยันจาก state_changes ที่ LLM คืนมาจริง)
    ตาที่ 7 "เปิดดูช่องส่งของด้านหลัง"  ช่องส่งของเป็นโครงสร้าง ไม่ใช่หลักฐาน
        โหมด A  allowed=True  state_changes={}                         อนุมัติแต่ไม่บันทึกอะไร
        โหมด B  allowed=True  state_changes={'unlocked_add':'supply_hatch'}
    ตาที่ 8 "ดูเส้นลวดทองแดง"  ลวดซ่อนอยู่ในช่องส่งของ
        โหมด B ผ่านเพราะเปิดช่องแล้วจริง
        โหมด A ผ่านทั้งที่ในสถานะของมันช่องนั้นไม่เคยถูกเปิด -> สถานะเป็นไปไม่ได้

    สรุปกลไก โหมด A "ตัดสินถูก" แต่ "ลงบัญชีผิด"
    การทดลองที่หนึ่งมองไม่เห็นข้อนี้ เพราะรีเซ็ตสถานะจาก checkpoint ทุกคำสั่ง
    ความผิดพลาดจึงไม่มีทางสะสม

ข้อจำกัดที่ต้องเขียนในเล่ม
    1. n=1 บท สรุปอะไรไม่ได้ ต้องรัน EP2 EP3 ให้ครบ
    2. พอสถานะสองโหมดแตกกันแล้ว prompt ที่ส่งเข้า interpret ก็ต่างกัน
       จึงแชร์ ParsedCommand ไม่ได้อีก ความแปรปรวนจากการสุ่มของ LLM
       กลับเข้ามาเป็นตัวแปรที่สอง
       ข้ออ้างของการทดลองนี้จึงเป็น "ระบบทั้งระบบ B รักษาความถูกต้องของสถานะได้ดีกว่า"
       ไม่ใช่ "ใครเป็นผู้ตัดสินคือสาเหตุเดียว" อย่างการทดลองที่หนึ่ง
       สคริปต์แชร์ผลตีความให้ตราบใดที่สองสถานะยังเหมือนกันเป๊ะ เพื่อลดตัวแปรนั้นให้น้อยที่สุด

ทำต่อ
    python run_episode.py          รันต่อจาก cache จะเริ่มที่ EP2
